# Design decisions

Each entry is a decision that is not obvious from the code, with the reason. Change the decision only with a reason at least as good, and record it here.

## Stateless CLI, not a daemon

A one-shot process per command, state on disk (`SessionStore`). Reasons: TCC grants attach to the host that runs amcu (terminal, agent host), so a rebuilt binary loses nothing; an agent can call it from any shell; nothing survives a crash to be in a wrong state. Cost: no AXObserver across calls, so settle detection and index reuse are done inside each command (`Settle`, `previous` snapshot). An MCP server wrapping the same `Commands` layer is the planned way to get a long-lived process without giving up the CLI (see Backlog). The resident processes today are the optional stage's: a holder that keeps the virtual display (it lives only as long as the process that created it) and the host that does everything else.

## Background delivery: fields 51/52 plus `CGEventSetWindowLocation`

Measured on macOS 27: window-id fields alone deliver to the window but land at its corner; `CGEventSetWindowLocation` alone is not routed at all; both together land exactly. The symbol is private, so `SelfCheck` clicks amcu's own throwaway window at an asymmetric point and caches the verdict per OS build. `--mode auto` uses routing only when the verdict is usable, otherwise falls back to an AX press at the point (`AXHitTest`); scroll/drag refuse. Foreground is never chosen automatically.

## Indices are stable identities (since 0.9.0)

Identity = FNV-1a over parent identity + role|subrole|identifier|label + ordinal among same-key siblings. Value, state, frame are excluded so an edited field is "changed", not "removed + added". Matching identities keep their index; new nodes take fresh indices after the previous maximum; a removed index is never reused in a session (an agent holding an old number gets `stale_snapshot`, never a different element). Numbering restarts when fewer than 40 % of nodes match (different window, rebuilt UI), and the diff then prints the full tree. Acting still resolves by `path` (AXChildren indices) and re-verifies role/subrole/identifier/label; identity is only for numbering and diffs.

## Observe after act

Every acting command settles (`Settle.wait`: at least `min`, until `quiet` seconds without AX notifications, at most `max`, plus `AXElementBusy`), then re-captures the session's snapshot and prints the diff. Wisp/Sky do the same and it is the single largest token saving: the agent otherwise re-reads the whole tree after each click. Observation only happens when the session already holds an accessibility snapshot of the same pid (a bare `type` into an unsnapshotted app has nothing to diff). `--no-observe` skips the re-capture; settling still runs because the focus verdict and any read-back depend on it. Paste restores the pasteboard after settling, which replaced a fixed 120 ms sleep.

## Snapshots are shaped

Structural containers with no label/value/action are skipped (children still walked, paths preserved), labelled compact controls are not expanded unless a direct child is actionable, tables report only rows on screen (`AXVisibleRows`, else intersection with the nearest `AXScrollArea`). Everything hidden is counted in the footer; `--no-shaping` is the escape hatch. `--query` filters after capture so all indices remain valid.

## Refuse rather than guess

Ambiguous app names, disabled controls, stale indices, foreground delivery to a non-frontmost app, password managers, out-of-range numbers: all errors with `nextSteps`. The alternative (do something plausible) produces the silent misclick class of bug that costs more than any refusal.

## Text before pixels

Accessibility tree first; `scan` (Vision OCR) only when the window is accessibility-blind, and its marks expire after 60 s because they cannot be re-verified. `docs/browser-use-ideas.md` records the evidence (SeeAct: text grounding 39 % vs set-of-marks 20 %).

## Browser: extension + native messaging, not CDP port, not AX

The user's own Chrome with logged-in sessions, no restart, no debug port for pages to probe, no token: the OS pins which extension id may talk to the host binary. Reading is a content script (no debugger attached, no infobar); acting goes through `chrome.debugger` so events are trusted and reach background tabs. `amcu lab` covers what an extension cannot (other extensions, chrome:// pages, network interception) with a throwaway profile. Driving Chrome through macOS AX remains possible (`snapshot --app com.google.Chrome`) as the no-setup path.

## Safari: a relay, long polling, and synthetic input (since 0.10.0)

Safari loads only Safari Web Extensions packaged in a signed app, routes `sendNativeMessage` to that app's sandboxed `.appex` one message at a time (`beginRequest`), and gives extensions no `chrome.debugger`. Decisions:

- **The bundle is assembled from the amcu binary, not compiled.** App executable and appex executable are both copies of amcu; the copy that finds itself inside an `.appex` calls `NSExtensionMain` (resolved with `dlsym`, the entry point Xcode links appexes against) and the principal class `AmcuSafariWebExtensionHandler` lives in AmcuCore. Plists and extension files are generated, `codesign` signs. So `amcu browser install --browser safari` works from the release tarball without Xcode, and the bridge is always the same version as the CLI that installed it. The converter's Xcode project was not committed: it would need Xcode to build and would drift from the binary.
- **Loopback TCP with a per-install token between appex and relay.** The appex is sandboxed. A Unix socket in a shared app-group container needs an app group, which ad-hoc and self-signed builds cannot claim; reaching into the appex's own container from the CLI triggers macOS's "access data from other apps" consent prompt. `com.apple.security.network.client` lets the sandboxed appex connect to 127.0.0.1 (measured: works, no prompt; loopback is exempt from Local Network privacy). The port and a 24-byte token are written into the appex Info.plist at install; the relay answers nothing to a connection without the token (a web page's fetch to the port gets an empty reply). The CLI side stays a 0600 Unix socket.
- **The relay is the container app's executable, started on demand.** The CLI spawns it (setsid, detached) when `--browser safari` finds no relay; it exits after 30 idle minutes. No LaunchAgent: that would add a "Background Items" notification and a permanent process for an opt-in feature. Its socket speaks the native-host protocol, so `BrowserClient` and every browser verb work unchanged; `hello` adds `ready` (the extension polled within 45 s), and default browser selection skips an unready relay.
- **Long polling, not a push channel.** The extension sends `poll`; the relay holds it up to 15 s (below any plausible Safari native-message timeout) and answers with a queued request or `idle`. With the relay down the appex answers at once and the extension retries every ≤3 s. A request while nothing polls fails in 8 s with `bridge_unavailable` and doctor's next steps instead of hanging for the full timeout. Safari profiles each run the extension; the relay pins the first profile that polls so tab ids stay coherent.
- **Synthetic input, labelled.** Clicks are the pointer/mouse event sequence at the measured point (covered targets still refused), keys are keydown/keypress/keyup plus the reproducible default actions, text goes through `document.execCommand('insertText')` (the browser's editing path; frameworks see real input events) with a value-setter fallback. Every result carries `synthetic` and the CLI prints it. Pretending these were trusted would be the silent no-op class of bug on pages that check `isTrusted`.
- **No amcu window in Safari.** `windows.create` cannot open an unfocused window in Safari, so a new window would raise Safari over whatever the user is doing. Tabs open unselected in the user's front window instead (`tabs.create({active:false})`); the cost is a visible tab in their strip and no screenshots of it until selected (`captureVisibleTab` sees only the selected tab).
- **Refuse what cannot be honest.** console, network, dialog, drag, resize and window management fail with `unsupported` and a next step (Chrome, `amcu lab`, or desktop amcu on the Safari window), in the relay before any round trip and again in the extension.
- **Signing.** Developer ID if present (Safari then needs no "Allow unsigned extensions"), else `AMCU_SIGN_IDENTITY` if it names an identity in the keychain (a stable designated requirement across reinstalls), else ad-hoc. Doctor cannot read the "Allow unsigned extensions" switch; it infers it from the extension not polling and lists the three owner steps.

## The amcu window is created minimised, and stays so (since 0.11.0)

Measured on macOS 27: `chrome.windows.create({focused:false})` does not take focus, but Chrome orders the new window directly below its own main window, which is above everything else the user has — so the first `tab --new` of a session covered whatever they were reading unless Chrome's main window hid it. Chrome's extension API refuses bounds that are not at least 50 % on a display ("Bounds must be at least 50% within visible screen space"), so the AeroSpace trick of hanging the window off the screen edge is not available from the extension (it works through accessibility `AXPosition`, but that would need the CLI to find the window by frame after every creation). Minimised was assumed to stop rendering; measured, it does not: `ensureAttached` turns on `Emulation.setFocusEmulationEnabled`, which holds a capture lock on the page, so `document.visibilityState` stays `visible` and a clock in a minimised window advanced between two screenshots. The window is therefore created with `state: 'minimized'` and screenshots no longer restore it; `window --hide` minimises, anything that focuses it (`--show`, `--activate`) restores it first. The cost is a Dock thumbnail per profile and one minimise animation when the window is created.

The window id is kept in `chrome.storage.local`, not session storage: reloading the extension (what `browser install` asks for) empties session storage and closes the extension's own pages, the pinned one included, and the old code then opened a second window. Window ids are unique per browser run, so `onStartup` forgets the id; the pinned page is put back whenever the window is looked up and found without it. `extension.reload` first opens a blank tab when the pinned page is the window's only tab, because the window would otherwise close with the page — and Chrome unloads a profile whose last window closes, taking the extension, the native host and every session's state with it (measured: the profile vanished from `amcu browser doctor`). `window --close` refuses in that same last-window situation; `--force` keeps the old behaviour for the agent that means it. The desktop `window --move` now reads the frame back after settling and reports where the window landed, because Chrome answered an `AXPosition` write with its own placement before settling.

## Windows on other desktops are reached, desktops are never created (since 0.11.0)

The request was "work on a virtual desktop so the user is not disturbed". With SIP on there is no silent way to create a Mission Control desktop (yabai needs its Dock scripting addition; Hammerspoon drives Mission Control visibly) and, between macOS 14.5 and 26.3, no way to move another application's window to one (`SLSMoveWindowsToManagedSpace` ignores cross-process calls; the compat-id workaround was removed in 15.0; 26.4 reopened it through a bridged operation whose symbol has to be scraped from SkyLight's symbol table). amcu therefore does not try. What it does instead is make the user's own arrangement work: a window the user put on another desktop, or minimised, is driven as if it were in front. Measured on 27.2 with a Chrome window on another desktop: `kAXWindowsAttribute` omits it; the window server lists it (`CGWindowListCopyWindowInfo`, off-screen, named); `_AXUIElementCreateWithRemoteToken` with yabai's 20-byte token (pid, 0, `0x636f636f`, element id) reaches its element by trying ids from 0 (found at 1583, 34 ms); the tree, `snapshot`, a routed coordinate click (page reloaded, frontmost application unchanged) and `screenshot` all work. Only off-screen windows with a name and at least 100×100 are probed, because every miss costs a full id sweep (~0.7 s) and a browser has a dozen nameless helper windows. For capture, ScreenCaptureKit handled the Chrome window on another desktop here, while the research probe's own 300×200 window on another desktop got `SCStreamErrorDomain -3811`; `SLSHWCaptureWindowList` (what cua and AltTab use) is tried first for such windows and the result says `via: window-server`. A minimised window is not composited: both paths returned a single-colour frame for one whose page had changed after minimising, so `screenshot` warns and points at the tree or `amcu browser screenshot`.

## Pointer events carry both window-field pairs and the target pid (since 0.11.0)

Fields 51/52 are private window-number fields; the public `kCGMouseEventWindowUnderMousePointer` pair is 91/92, and Chromium's synthetic-event filter also reads the target pid (field 40). Sky and cua set all of them; amcu set only 51/52, which routes on its own (measured, and still the pair SelfCheck proves). All are set now, and the pid field is set on every background post, keyboard included. The AppKit e2e probes pass unchanged; Chromium web content through the desktop path was not re-measured beyond a Chrome toolbar click.

## One connection per profile, chosen explicitly (since 0.10.0)

Chrome runs a separate copy of the extension in each profile, and each copy spawns its own host and socket, so profiles were always separate connections; what was missing was telling them apart. The extension generates an instance id once (kept in `chrome.storage.local`) and an optional label, and sends both in its hello. The host infers the profile directory rather than being told it, because an extension has no API that names its profile: the extension writes a key named `amcu_instance_<id>` and the host byte-searches `<user data dir>/*/Local Extension Settings/<ext id>/` for it. leveldb keeps keys verbatim in its write-ahead log; table files may be snappy-compressed, so the extension re-writes the key at every start to keep a plain copy in the newest log. The user data dir is the parent browser's `--user-data-dir` (read with `KERN_PROCARGS2`, which makes `amcu lab` profiles work) or the browser's default. Exactly one hit or nothing: a copied profile with the same id yields no answer instead of a guess. The display name comes from `Local State` and is re-read each time because users rename profiles. Since 0.11.1 the CLI repeats both lookups when the host answers without them: on macOS 27 the System Policy sandbox denies a Chrome-spawned host every read under Chrome's data directory (`deny(1) file-read-data …/Google/Chrome/Local State` in the sandbox log; the same binary started from a shell reads it), while the CLI runs under the agent's host, which usually may.

Selection refuses rather than guesses. Before 0.10 two Chrome profiles meant `select` silently took the first socket by name order, which is the silent-misclick class of bug pointed at an account: the agent posts as the wrong shop. Now several candidates and no narrowing selector is `ambiguous_browser`, listing each candidate with the shortest flag that picks it (label, then profile dir, display name, instance id, else `NAME:PID`). `--browser chrome` matching two is refused too. The one ambiguity kept is the old "a single Chrome among other browsers wins", which never mixed up accounts. `--profile` matches in tiers, first hit wins: label, profile dir, display name, whole id (exact, case-insensitive), then id prefix — so a label the user chose beats a display name that is the same word, and a short label is not shadowed by an id that starts the same way. Every browser result carries `connection` (pid, instanceId, label, profileDir, profileName) so the agent can check which account acted. `label` refuses a name another connection already answers to, and reports success only after a fresh discovery shows the host carrying it.

`browser install` asks running extensions to reload so they pick up new files; `--no-reload` exists because a reload drops the extension's debugger attachments and session state (current tabs per `--session`) in profiles the user is working in, and an agent updating the binary should not do that unasked.

## Policy file over compiled lists

`~/.config/amcu/policy.json` extends the sensitive-app deny/allow lists, the input-immune list, and settle timing. The built-in lists stay as the floor; users with unlisted vault apps should not need a rebuild.

## Event tagging

All synthesized events carry `0x414D4355` in `eventSourceUserData`. Nothing consumes it yet; it exists so a future intervention monitor or the self-check can distinguish amcu's input from the user's without heuristics.

## Each agent has a session of its own (since 0.11.2)

Measured on 27.2 with two agents on one machine: one ran `amcu scan --app cc.uoox.aaaui` without `--session`, the other ran `snapshot --app com.apple.calculator` and then four `click --app com.apple.calculator --element N`, also without `--session`. The scan landed in between, so all four clicks resolved against the scan and were routed into the AAA window at the recognised texts, each reported as `click ok`. Two causes, both fixed. First, `--element` takes its target from the snapshot (`pid:` of `snapshot.app`) and ignored `--app`; `elementTarget` now refuses with `stale_snapshot` when a named `--app` is another process. Second, `default` was one namespace for every agent on the machine, and the guide's advice to pass `--session` was not followed in practice (neither agent did). Without `--session`, the name now comes from the environment the host gives every command: `AMCU_SESSION`, else `AAA_SESSION` (aaa-daemon, any agent), else `CLAUDE_CODE_SESSION_ID`, else `default`. The browser's current-tab namespace follows the same rule, because two agents sharing a current tab is the same failure with page actions. Values are sanitised into file-name-safe characters; `doctor` prints the session in effect and its source. An agent that relied on `default` to share state across hosts must now pass `--session default` explicitly.

## The stage: a display the user never sees (since 0.12.0)

The 0.11.0 request ("work on a virtual desktop so the user is not disturbed") is met with a display instead of a Space. A window on another desktop or minimised is not composited — captures are stale, some applications throttle — while a window on a virtual display is drawn like any other and is still nowhere the user looks. Measured on 27.2 (26B123), all with the user working on the main display: AXPress, routed coordinate clicks and keyboard input (TextEdit took "hello virtual display 你好") land on windows there; window captures and whole-display captures are current; the target never became frontmost; when the display goes, macOS puts each window back where it was before it was moved.

- **`CGVirtualDisplay`, resolved at runtime.** CoreGraphics exports the classes (they are in its `.tbd`) but no header declares them. `VirtualDisplay` finds them with `NSClassFromString`, checks every selector with `class_respondsToSelector` (`unavailableReason`), sets descriptor and settings through KVC and sends `alloc`/`initWithWidth:height:refreshRate:`/`initWithDescriptor:`/`applySettings:` through `objc_msgSend` cast to exact signatures. A Swift metatype of an Objective-C class points at Swift's wrapper metadata, not at the class object: passing it as the receiver crashed in `objc_msgSend` at 0x310 (the wrapper's kind word, 0x305, read as an isa); bridging through `AnyObject` gives the class object. The mode is given in points with `hiDPI` = 1 and the pixel maximum at twice that; a mode given in pixels came up as an unrelated 1920x810 mode. The stage matches the main display's size and scale, so a window keeps its size and captures stay at 2x.
- **Placed off the corner, for the session.** A new display comes up beside the main one (left or right; it varied by identity). With the Dock on the right, the Dock window jumped onto a stage beside the main display and came back about 0.8 s later when the stage moved to the corner; at the corner, the main display keeps its Dock (its visible frame stays 60 pt short, the stage's is full width). An origin far away is pulled back to the corner: macOS keeps displays touching, so one shared point is the minimum. The origin is configured `.forSession`: WindowServer then brings the same identity up at the corner directly (measured on the next creation), so only the first start after login can make a side Dock flicker, and the start note says so. `.forAppOnly` is not remembered. Displays rearranged later are re-checked and the stage goes back to the corner.
- **Found by identity.** Vendor 0x616D ("am"), product 0x6375 ("cu"), serial 1; `CGDisplayVendorNumber`/`ModelNumber`/`SerialNumber` report them back. Any amcu process finds the stage without asking the host: `windows` marks windows on it, `doctor` reports it, and `--mode foreground` refuses a point on it (the cursor would go where the user cannot see, and the guard pulls it straight back).
- **A resident host, started on demand.** `amcu stage serve` stays up: started detached (setsid) like the Safari relay, single instance through `flock` on `stage.lock`, newline JSON over `stage.sock`, requests run on the main thread where the AX observers, timers and panel live. Responsibility is inherited, not disclaimed, so the host has the grants of the command that started it (`answersFor` in status). What TCC does when that responsible process (aaa-daemon) restarts under a running host is not measured. An empty stage exits after 15 minutes; SIGTERM brings windows back before the display goes.
- **The display is kept by a process of its own (since 0.13.0).** The display lives exactly as long as the process that made it. Kept by the host (0.12), every upgrade meant `stop` and `put` again: the windows came back onto the user's screen, and once stayed there half a minute because the browser had come to the front in the gap and `put` refused it. Now the host starts `amcu stage hold` (from its own copy, `stage-display/amcu`; an NSApplication accessory that does nothing else and rarely changes), which records itself in `stage-display.json`. A new host takes over a display that is up (`StageDisplayHolder.current()`: record, live pid, display online with the stage identity) and carries on from `stage-state.json`, which every host writes after each change: records with their homes, what is followed, what the user holds, notes, activity, whether the stage window was open. The lock is held only by a running host or one on its way out, so a new host waits up to 10 s for it. `handover` (and `amcu stage restart`) writes the state, gives up the socket and exits without touching the display; the holder goes on `stop`, on idle exit, when the system ends its display, or when no host has answered for 60 s, so a host that died does not leave windows on a display nobody shows. The host also watches the binary it was copied from (`--source`): when it changes and has stayed unchanged for 4 s, and the user is not working in the stage window, the host clones it, starts it and hands over — installing amcu updates the stage with no window moving. If no holder can start, the host keeps the display itself as before, and a restart cannot keep it. A host from before 0.13 cannot hand over: `stage restart` then stops it and puts its windows on a new stage, waiting while the user is working in an application they touched since the stop (the HID idle time is older than the stop otherwise: the application came forward by itself); measured 1.8 s from 0.12.1. Measured on the first day, and fixed: the holder, spawned with the host's descriptors, kept the host's lock after the host left (`flock` belongs to the open file), so the next host waited 10 s and gave up, and the holder, finding no host for 60 s, let the display go — children are now spawned with `POSIX_SPAWN_CLOEXEC_DEFAULT` and the lock is opened `O_CLOEXEC`. And while the displays sleep (here after 5 idle minutes) `CGGetActiveDisplayList` is empty, so a stage looked up there was "gone" and a new host tried to make a second display with the same identity, which the system refused: the stage is looked up among online displays. A display whose holder ended while the displays slept stayed online until they woke. When a display with the stage's identity comes back, macOS puts the windows that were on it back where they were on it (measured: the windows dropped on the main display returned to their stage positions when a new holder made the display again; their homes were lost, as `put` found them on the stage). A handover with three windows on the stage took 0.4 s; an install was picked up 4.5 s after the binary changed.
- **A locked screen loses no records (since 0.14.0).** While the screen is locked, accessibility lists an application's windows with no ids and 0×0 frames, so a host that took over then matched none of the records it was left and dropped them: the three Chrome windows came back "not put here by amcu", and a put window lost its home. Now a host does not upgrade itself while `CGSSessionScreenIsLocked` is set (an install is picked up after the unlock), and a host that takes over anyway (a 0.13 host upgrading, `stage restart`) keeps every record whose window still exists, writes it on to the next host, shows it in status with its origin and home, and matches it once the screen is unlocked (measured on the test stage: kept across a locked takeover and a locked restart).
- **Moves are read back.** `put` writes `AXPosition` (keeping the window's offset from its display's top-left, clamped below the stage's menu bar), then reads the frame until it reaches the target or stops changing; at least half of it on the stage counts. The frame it left is its home, and `release` puts it back there; a window amcu did not put on the stage goes to the centre of the main display's usable area. Minimised windows are refused: restoring one would animate it out of the user's Dock. `put` refuses the frontmost application unless `--force` (an application that brought itself forward at launch).
- **New windows are followed.** macOS opens a new window where the user is (measured: TextEdit's ⌘N document and its Open panel; another probe found an `NSWindow` created at the stage's coordinates placed on the main display). An `AXObserver` on each staged application's `kAXWindowCreatedNotification` moves standard windows, dialogs and floating panels over 0.15 s after creation (measured: Calculator's About window). Skipped while the application has keyboard focus, read from the system-wide AX element (`NSWorkspace.frontmostApplication` lags by up to a second): then the user made the window. The window is visible on the user's screen for that fraction of a second; `--no-follow` turns following off.
- **The cursor guard.** Global and local monitors for mouse moves and drags, plus a 0.5 s timer for warps no event reports; a cursor inside the stage goes to the nearest point of a user display (`CGWarpMouseCursorPosition`, then `CGAssociateMouseAndMouseCursorPosition(1)` so the pointer does not freeze for a quarter second). Whether the single shared corner lets a real pointer through at all is not measured.
- **The user can take a window over; an agent acting on it takes it back.** Agreed with the user (the Mika flow: the small window only shows, acting happens with the application back on the user's screen, then it is handed back and the agent looks again before continuing). Driving the pictures like a remote desktop was rejected: forwarded synthetic events do not reach WeChat, slider checks or input methods, and real events would need the cursor on the stage, against the cursor guard, with focus moving anyway. Clicking a window's picture takes it over with the clicked spot under the cursor: the picture has the window's proportions, so the click is a fraction of the window (`point(in:fraction:)`); the window moves so that spot rests under the cursor (`alignedOrigin`, clamped below the menu bar and clear of the Dock), is raised and its application brought to the front; the click is not replayed, because the picture may be a frame old. The "take over" button does the same to the window's home, and `release --activate` counts as a take-over too. Each take-over records where the window was on the stage; "hand back" puts it there again and, if the application still has the keyboard, gives the keyboard back to the application that had it before. A held window keeps its card (outlined, "you hold it", its picture still live, a click brings it to the front); "hand back" and "release" sit in the header next to the cursor-guard chip and act on everything held, as the user asked: one click each. Release lets the windows go for good: they stay on the user's screen, off the stage, and amcu acts on them there like on any window. Until 0.12 every acting verb on an application with a held window failed with `taken_over`, a lock per application (per browser process for page verbs) so no agent could steal focus through a sibling window. In practice one held Chrome window stopped every agent in every profile (the xhs-comments panel drives two of them on the stage), and the user decided otherwise: an acting verb on a held window hands it back first and then acts (`Stage.handBackBeforeActing`, the window from `--window-id`/the snapshot, else the application's focused window; for page verbs the tab's window, from the session's current tab and the stage window's title pairing), and other windows are not held back. `taken_over` remains only for a hand-back that failed. While anything of an application is held, the host still leaves its new windows on the user's screen. The host writes what is held to `stage-takeovers.json`; the CLI reads it before acting (no round trip) and ignores a file whose host is gone.
- **The stage is an app in the Dock, not a menu bar icon (since 0.14.0).** The user asked for an app with a window rather than an icon in the menu bar. The host is that app: `stage-host/amcu.app`, assembled at run time around the host's copy of the binary (an Info.plist, an icon drawn in code), because a bare executable shows in the Dock and ⌘-Tab as a generic program; nothing is installed into /Applications, and the bundle answers for no permission of its own — the host is still spawned by the command that started the stage and acts with that command's grants. It starts as an accessory application and becomes a regular one only once it is up: a regular application exec'd outside Launch Services can come to the front by itself, and a host starts on an agent's `put` and on every upgrade, which must never take the user's keyboard. Clicking the Dock icon opens the window; closing the window keeps the stage; quitting the app closes the stage, after a confirmation naming how many windows come back (logout and shutdown skip it), because a quit that left the holder alone would drop the windows on the user's screen a minute later. Opened from Finder or Spotlight with no stage running, it only says that a stage starts when an agent puts a window on it: a stage started by Launch Services would answer for the app, which has no Accessibility or Screen Recording grant. A 0.13 host upgrading copies the new binary to its old bare path; that process installs the bundle and restarts from it before taking the lock.
- **The stage window does not take focus by appearing.** `amcu stage show` and a restored window come up with `orderFrontRegardless`, not `makeKeyAndOrderFront`, so the user's application keeps the keyboard until they click the window; buttons, tabs and pictures accept the first mouse, so one click works while another application is active. The content is SwiftUI in an `NSHostingView` under a transparent title bar, following the system appearance; empty parts of the tab strip and window bar drag the window and double-click as the system setting says.
- **The stage window has a tab per staged window (since 0.14.0).** The user asked for tabs like Chrome's and VS Code's, along the top or down the left as they choose (View menu, the strip's button, its context menu; remembered in the app's defaults). Tabs keep their order; a window that comes to the stage opens a tab at the end; a closed tab selects the next one (`StageTabOrder`), and order and selection survive a host handover in the state file. Top tabs sit in the title bar centred on the traffic lights (their position is read from the window, so a system with other metrics still lines up), share the width down to 96 points and then scroll. The selected window fills the rest: a picture of that window alone at most at its actual size (a ScreenCaptureKit stream, `desktopIndependentWindow`, at most 5 fps, frames only when it changes, 2× up to 1200 px on the long side), only for the selected tab — the others keep their last frame — and beside it, or under it below 900 points, what agents did, its browser tabs and where it came from. 0.12.0 showed the whole stage as one picture, where a calculator was a speck; a list of every window on the Mac was rejected by the user; 0.12.1–0.13 showed a grid of cards, which the tabs replace. A browser window on the stage lists its tabs from `tabs.list` of each profile's extension: the active one highlighted, the ones with amcu's debugger attached marked "amcu", more than six folded. A window server window and a tab share no id, so they are paired by title (the window is titled after its active tab, sometimes shortened in the middle with "…"); windows with the same title — two profiles on the same site, all one process — are paired in creation order, since window server numbers and browser window ids both only grow (checked against each profile's saved window placement), and left without tabs when the counts disagree. All of the browser's windows take part, on the stage or not, so a twin elsewhere is told apart. Pictures and tabs run only while the window is open and not minimised; tabs are fetched off the main thread, only from browsers with a window on the stage.
- **The stage window shows what agents do.** Every acting verb, desktop and page, ends by telling the host what it did to which window (`StageReport` → `activity`, fire-and-forget; only when a stage display is up and, for desktop verbs, the window is on it): the session, the kind, what it acted on as the accessibility tree or the page names it, how many characters (never which), the keys, the menu path, the site, and where in the window as a fraction. The host keeps it for windows on the stage or held, maps a page verb's tab to its window through the same title pairing as the tab list (asking the profiles off the main thread when the tab is unknown), and the card shows the last three lines, a "session at work" badge on the picture for 15 s, and a ring where a click landed. The same action again and again in a row (the xhs-comments panel runs a script in each window every second or two) is one line with a count, so the panel's polling does not push everything else off the card. A page element is named by its text (`button "发送"` reads 「发送」). The look is checked with `amcu stage preview`, which draws the window with made-up windows on the stage display, where nobody sees it, and captures it: real windows (a bank report was on the stage) never need to be in the picture. The extension reports a click's place in the window from the top frame's inner and outer size (page zoom scales the viewport, not the window); an extension not yet reloaded gives no place, and the line still shows.
- **Links the user opens stay off the stage (since 0.14.0).** A link opened from another application goes to the browser's last active window of its last used profile, and an agent acting in a staged window makes that window the last active one; the link then opened on a display the user never sees. The extension recognises such a load by its transition, `start_page` (what Chrome reports for URLs from other applications and the command line; tabs amcu opens, links clicked in a page, typed URLs and bookmarks report others), outside the first 20 s after the browser starts (session restore). The host decides, because only it knows the stage and can reach every profile: the window the user focused last, across the browser's profiles with the extension (focus times kept by each profile's worker), never one on the stage or minimised; another profile only when focused more recently than this one's best window, so without evidence the link stays in its profile; else a new window centred on the main display. The tab is moved (keeping the loaded page) or, for another profile, opened there and closed here; the staged window's previous active tab comes back to the front, so the agent's page is as it was. A window's only tab is never moved out (that would close an agent's window); it goes back instead, unless the window was made for the link, which then moves whole. A window the user holds is on their screen and is left alone. The stage notes each redirect (`amcu stage status`, recent). Safari is not covered.
- **Prompts go to the user, and the stage window to a display they see (since 0.14.1).** Found the night after 0.14.0: while the displays slept, an OrbStack Helper local-network prompt (drawn by UserNotificationCenter) opened on the stage and waited there two hours unanswered, and its tab could not take it over: the window the window server listed on the stage (78786, 410×401) was not the one accessibility knows (78785, 260×251, inside it). The stage window open on the test stage had moved onto the other stage's display, and showing it again left it there: it was placed once per host, and only its own stage counted as a stage. Now every tick (2 s), once the screen is unlocked, the host moves the accessibility windows of UserNotificationCenter, SecurityAgent, CoreServicesUIAgent and universalAccessAuthWarn that are on the stage to the middle of the main display's usable area, and does not try again a window that refused (measured on the test stage: a `CFUserNotification` moved onto it was back in 2 s). Other applications' windows found on the stage stay, a tab each: a staged application's dialogs belong there, and the user can take any of them over. The stage window is placed whenever it is shown and whenever the displays change: with no part on a display that is not an amcu stage (any serial), it goes to the middle of the main display (measured: moved onto the real stage, shown again, back at the centre).
- **Updating the extension keeps sessions.** Reloading it empties `chrome.storage.session`, which holds each session's current tab, and broke agents mid-task (the xhs-comments panel); `amcu browser install` now reads every profile's sessions before asking it to reload and gives them back (`sessions.restore`, only tabs that still exist, only sessions that did not pick a tab meanwhile) once the new worker connects. Measured on the first install (from 0.11.1): both xhs-comments sessions kept their tabs; jtf's 10 sessions all pointed at tabs closed long before (a session keeps its tab id after the tab closes), and the report now says so instead of "0/10". A BitBrowser profile did not come back: a Chromium profile with Developer mode off disables an unpacked extension when it reloads (`unsupportedDeveloperExtension`; BitBrowser starts its profiles with `--load-extension` and Developer mode off, so it ran until then). Turning Developer mode on brings the old version back at once, and a second reload loads the new one; the install report now names a profile that did not reconnect within 15 s and says this.
- **The host runs from its own copy of the binary.** replayd tells its clients apart by executable path: while the host held capture streams, `amcu screenshot` run from the same path hung in replayd (4 of 5 runs, and on after the streams stopped), while a copy anywhere else, even beside it, never did. On 27.x the window server's own capture (`SLSHWCaptureWindowList`) is proxied through ScreenCaptureKit too, so it is no way around. The host is spawned from `~/Library/Caches/amcu/stage-host/amcu.app/Contents/MacOS/amcu`, a fresh APFS clone (signature included) moved into place at every start; a host still running from the old copy keeps its file. A ScreenCaptureKit capture in the CLI waits at most 6 s and then fails with `timeout`, without the window-server fallback, which would wait on the same daemon.
- **Taking over raises through accessibility.** "Take over" brings the window back to its home and raises it through accessibility (`kAXMainAttribute`, `AXRaise`, `kAXFrontmostAttribute` on the application element), because since macOS 14 an application that is not itself active — the host never is — may not hand activation to another through `NSRunningApplication`.

## Deliberately not adopted

- **Animated agent cursor / banner / Esc-to-stop**: contradicts "do not disturb the user". (A Mika-style capsule with progress and stop belongs in the agent host, AAA, not in amcu; the stage window only shows the stage.)
- **Auto-attached screenshots when the tree is empty**: `scan` gives text with positions instead; pictures are opt-in.
- **`AXEnhancedUserInterface` on Chromium hosts**: makes `AXPosition` writes be ignored, breaking `window --move`; only `AXManualAccessibility` is set.
- **Auto-launching from `--app`**: launching is visible; it is the explicit `launch` verb (which still does not activate).

## Backlog

- **Stage measurements still owed**: whether a real pointer crosses the single shared corner (the guard pulls it back either way); what TCC does to a running host when its responsible process (aaa-daemon) restarts. (`type --text "6*7="` delivers only "6" to Calculator on the main display as on the stage: a Calculator/`type` matter, not the stage.)

- **MCP server** (`amcu mcp`): stdio JSON-RPC over the same `dispatch`; one process per agent session keeps the AXObserver subscribed, the previous snapshot in memory, and removes process start-up per call. Tool descriptions should be one line each and point to a `guide` tool; the diff output is what keeps per-call tokens low, not the transport.
- **Synthetic activation experiment**: three candidates, to be measured with the e2e ButtonProbe for whether AppKit stops making the target frontmost on a background mouse-down: an AppKit-defined `applicationActivated` event to the target pid (wisp); `SLPSPostEventRecordTo` with a focus record aimed at the target window only (Peekaboo's `BackgroundWindowActivationDriver`); cua's `activate_without_raise` (defocus record to the front process, focus record to the target, deliberately no `SLPSSetFrontProcessWithOptions`, with the known cost that the user's window needs a click to regain keyboard focus). Also cross-check wisp's claim that field 51 alone routes accurately without `CGEventSetWindowLocation`.
- **`CGEventSetWindowLocation` coordinate semantics by OS**: cua records that macOS 27+ takes window-local coordinates and earlier versions screen coordinates. amcu always passes window-local, so on 14–26 SelfCheck probably reports routing unusable and `--mode auto` falls back to AX presses. SelfCheck should try both and cache which one landed, per OS build.
- **Keyboard to Chromium/Electron targets**: cua posts with `SLEventPostToPid` (goes through `CGSTickleActivityMonitor`; `CGEventPostToPid` skips it) and, on macOS 14+, attaches an `SLSEventAuthenticationMessage` to synthesized keyboard events for Chromium-class targets (`+[SLSEventAuthenticationMessage messageWithEventRecord:pid:version:]`, 15+). Mouse events must not carry it. Worth measuring against Slack/VS Code before `type` claims to work there.
- **Chromium click primer**: cua sends a routed `mouseMoved` before the mouse-down (AppKit hit-tests against the window's last tracking state, stale for a background window) and a down/up at (−1,−1) to satisfy Chromium's user-activation gate. Measure on a Chrome page through the desktop path.
- **Key-focus theft by background menus**: a background application opening a popup, `<select>` or context menu calls `SLPSStealKeyFocusReturningID`; the user's window silently stops receiving keys, no application activates, FocusGuard sees nothing. cua's guard needs a resident process with a per-pid event tap; it is a concrete reason for the MCP/daemon item above.
- **Launch focus-steal undo**: `activates:false` does not stop Chrome/Electron from activating themselves at launch. cua re-activates the previous front application within 5 s unless the HID system saw a mouse-down or flags change in the last second (`CGEventSourceSecondsSinceLastEventType`), which is the test that makes an undo safe. It also reads the front process with `_SLPSGetFrontProcess` because `NSWorkspace.frontmostApplication` lags about a second; FocusGuard could use the same.
- **Batch attribute reads**: `AXUIElementCopyMultipleAttributeValues` once per node instead of one round-trip per attribute (cua); Sky goes further with `_AXUIElementCopyHierarchy`.
- **Action postconditions**: a `--expect "/text/"` polled within the settle window (terminator's `verify_element_exists`, cua's `verify_state`), distinct from the diff.
- **Background hotkey policy**: Peekaboo refuses ⌘W/⌘Q/⌘H/⌘M in the background because pid-posted chords have no receipt; amcu could do the same and point at `window --close` / `action`.
- **Lock screen**: `CGSessionCopyCurrentDictionary()["CGSSessionScreenIsLocked"]` (`Stage.screenIsLocked`, used by the stage host since 0.14.0) reported by doctor and on actions, so an agent does not work a locked session blind (wisp).
- **`amcu key` chord syntax** (`cmd+shift+t`) as an alternative to `--key t --mod cmd,shift`.
- Browser backlog with verdicts: `docs/browser-use-ideas.md`.
- **Safari wake-up push**: `SFSafariApplication.dispatchMessage` from the container app could wake a sleeping background page instead of waiting for its one-minute alarm; untested whether Safari delivers it to an unloaded page.
